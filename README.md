## Що свідомо не покрито

ТЗ просить покрити основні сценарії, тому решту відкладено свідомо. Нижче те, що **не перевірялось ні автотестами, ні вручну**, якщо не сказано інше.

### UI
| Що | Чому не покрито |
|---|---|
| Мобільна та адаптивна версія (viewport телефона й планшета) | Спершу пропущено ненавмисно (див. AI_WORKLOG, помилка №4). Тепер свідомо відкладено: пріоритет мають обовʼязкові пункти ТЗ (API, CI). Якщо лишиться час, буде дослідницький прохід через MCP у мобільному viewport. |
| Інші браузери (Firefox, WebKit/Safari) | Заради часу всі тести йдуть лише в Chromium. Додати браузер = додати project у [playwright.config.ts](playwright.config.ts). |
| Бокове меню: **Dynamic Catalog**, **Reset App State**, **All Items**, Close Menu | Поза основними сценаріями з ТЗ. Dynamic Catalog і Reset App State — першочергові кандидати на дослідження: про їхню поведінку поки нічого не відомо. |
| Пункт меню **About** | Веде на зовнішній сайт `https://saucelabs.com/` (видно в snapshot сторінки). Найімовірніше, так задумано, бо це сайт автора демо-магазину. Як саме він відкривається (та сама чи нова вкладка), не перевірялось. |
| Кнопки **Continue Shopping**, **Cancel** (обидва кроки чекауту), **Back Home**, **Generate PDF order** | Другорядна навігація, у ТЗ не вимагається. |
| Посилання у футері (X, Facebook, LinkedIn) | Зовнішні сайти, не функціональність магазину. |
| Користувачі `problem_user`, `error_user`, `performance_glitch_user`, `visual_user` | Навмисно «зламані» користувачі демо-стенду. ТЗ вимагає `standard_user`; `locked_out_user` покритий в UI-N1 як негативний кейс. |
| Граничні дані в полях чекауту (лише пробіли, спецсимволи, дуже довгі значення) | Покрито лише порожні поля (UI-N2). |
| Опис товару і `src` зображення в UI-02 | Порівнюються назва і ціна, для зображення перевіряється лише alt-текст. Опис не має ні ролі, ні test id, а текстовий локатор на кілька речень був би крихким. |
| Візуальна регресія, доступність (a11y), продуктивність | Окремі види тестування, поза обсягом ТЗ. |

### API
| Що | Чому не покрито |
|---|---|
| `PATCH /booking/:id` (часткове оновлення) | Флоу з ТЗ використовує `PUT`. |
| Фільтри `GET /booking?firstname=…&checkin=…` як окрема функція | Пошук за `firstname` використовується лише як допоміжний: в API-N2 доводить «бронювання не створено», а в API-01 перевіряється на позитивному випадку. Інші фільтри не тестуються. |
| Авторизація через `Authorization: Basic` | Документація описує її як альтернативу Cookie; тести використовують лише Cookie `token=…`. |
| Формати XML і `application/x-www-form-urlencoded` | Документація згадує їх, але флоу з ТЗ покрито в JSON. |
| Валідація окремих полів (неправильні типи, дати checkout раніше за checkin, відʼємна ціна) | Покрито лише відсутність обовʼязкових полів (API-N2). Інші варіанти — наступні кандидати, якщо буде час. |
| Контрактні тести через JSON Schema | Поза обсягом ТЗ; обʼєкт бронювання у відповідях порівнюється з очікуваним повністю (`toEqual`), тож зайві, відсутні чи інакше типізовані поля бронювання вже ловляться. |
| Навантаження, rate limits, термін дії токена | Документація про них нічого не каже; поза обсягом ТЗ. |

## Знайдені баги

**Як оформлено.** У звітах лише те, що перевірено фактично. Версії браузерів, клієнтів, ОС і часовий пояс зчитані з системи, роздільну здатність виставлено явно, а кожен доказ — файл, знятий під час відтворення. Формальної специфікації saucedemo немає, а документація restful-booker не описує помилок, тому в полі «Підстава» прямо сказано, на що спирається очікуваний результат.

**Баг чи спостереження.** Баг — коли система ламається або порушує те, що обіцяла (документацію, власні повідомлення, загальновизнану семантику HTTP для явного збою на кшталт 500). Спостереження — коли поведінка незвична, але нічого не зламано і нічого обіцяного не порушено. Очікування, які нічим не підтверджені, винесено в [Спостереження](#спостереження).

### BUG-001: Чекаут: замовлення з порожнім кошиком підтверджується як відправлене

**Оточення**
- Сайт: https://www.saucedemo.com, 25.11.2026
- Браузер: Google Chrome 157.0.8103.79 (ручне відтворення через Playwright MCP); Playwright Chromium 159.0.8154.6 (автотест)
- ОС: Windows 11 Pro 10.0.26200
- Пристрій і роздільна здатність: десктоп, viewport 1280×720
- Часовий пояс: UTC+02:00 (FLE Standard Time)

**Передумови**
- Користувач залогінений як `standard_user` / `secret_sauce`.
- Кошик порожній: на іконці кошика немає лічильника.

**Кроки відтворення**
1. Натиснути іконку кошика у верхньому правому куті. Відкривається `/cart.html` без жодного товару.
2. Натиснути **Checkout**.
3. Заповнити First Name: `John`, Last Name: `Doe`, Zip/Postal Code: `12345`. Натиснути **Continue**.
4. На сторінці «Checkout: Overview» натиснути **Finish**.

**Очікуваний результат.** Замовлення без товарів не підтверджується: застосунок не доходить до сторінки «Checkout: Complete!».

**Підстава.** Формальної вимоги немає. Очікування спирається на суперечність у самому застосунку: на кроці 4 сторінка повідомляє «Your order has been dispatched», тобто система стверджує, що відправила замовлення, у якому немає жодного товару (QTY і Description порожні, сума $0.00).

**Фактичний результат.** Кожен крок проходить без помилок. Огляд показує порожній список товарів, «Item total: $0», «Tax: $0.00», «Total: $0.00». Після **Finish** відкривається `/checkout-complete.html` із заголовком «Thank you for your order!» і текстом «Your order has been dispatched, and will arrive just as fast as the pony can get there!».

**Severity:** Major: порушено бізнес-логіку основного сценарію (оформлення замовлення), система створює і підтверджує некоректне замовлення.
**Priority:** Medium: сценарій не блокує покупку з реальними товарами, але дає змогу створювати порожні замовлення.

**Докази**
- [BUG-001-1-empty-cart.png](docs/bugs/BUG-001-1-empty-cart.png): крок 1, кошик порожній, кнопка Checkout доступна
- [BUG-001-2-overview-zero-total.png](docs/bugs/BUG-001-2-overview-zero-total.png): крок 3, огляд без товарів із сумою $0.00
- [BUG-001-3-order-complete.png](docs/bugs/BUG-001-3-order-complete.png): крок 4, «Thank you for your order!»

**Автотест:** UI-N3 у [tests/ui/checkout.spec.ts](tests/ui/checkout.spec.ts), позначений `test.fail()`. Тест не вимагає конкретного способу блокування (неактивна кнопка, помилка, редирект), а перевіряє лише те, що підтвердження замовлення не з'являється. **Обмеження:** якщо тест раптом стане «unexpectedly passed», це може означати і виправлений баг, і битий локатор: в обох випадках крок не виконується за таймаутом. Щоб їх розрізнити, тест записує в анотацію `blocked-at` крок і локатор, на якому зупинився (перевірено навмисно зламаним локатором Checkout).

### BUG-003: API: `POST /booking` без обовʼязкових полів повертає 500 Internal Server Error замість помилки клієнта 4xx

**Оточення**
- API: https://restful-booker.herokuapp.com, 25.11.2026
- Клієнт: curl 8.22.0 (x86_64-w64-mingw32) для ручного відтворення; Playwright 1.65.1 `APIRequestContext` (автотест)
- ОС: Windows 11 Pro 10.0.26200
- Часовий пояс: UTC+02:00 (FLE Standard Time)
- Браузер і роздільна здатність: не застосовуються (HTTP API)

**Передумови:** немає. `POST /booking` не потребує авторизації.

**Кроки відтворення**
1. Надіслати запит:
   ```
   POST https://restful-booker.herokuapp.com/booking
   Content-Type: application/json
   Accept: application/json

   {"firstname":"QaEvidence1795614618"}
   ```
2. Перевірити, чи створено бронювання: `GET https://restful-booker.herokuapp.com/booking?firstname=QaEvidence1795614618`.

**Очікуваний результат.** Відповідь зі статусом 4xx (найімовірніше 400 Bad Request), яка повідомляє, що бракує обовʼязкових полів. Бронювання не створюється.

**Підстава.**
- Документація ([api_data.json](https://restful-booker.herokuapp.com/apidoc/api_data.json), CreateBooking) позначає всі поля тіла (`lastname`, `totalprice`, `depositpaid`, `bookingdates.checkin`, `bookingdates.checkout`, `additionalneeds`) як обовʼязкові. Запит без них — помилка клієнта.
- Кодів помилок документація не описує, тому конкретний статус визначено за [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-15.5): 4xx означає помилку в запиті клієнта, а 5xx (розділ 15.6) — що сервер не зміг обробити коректний запит. Відповідь 500 на некоректний запит означає, що вхідні дані не валідуються і сервер падає всередині.

**Фактичний результат.** `HTTP/1.1 500 Internal Server Error`, тіло `Internal Server Error`, без пояснення, яких полів бракує. Бронювання не створено: `GET /booking?firstname=…` повертає `[]`.

**Severity:** Minor: дані не псуються і бронювання не створюється, але клієнт API не дізнається, що саме не так із запитом, а сервер реагує на помилку клієнта збоєм.
**Priority:** Medium: проблема проявляється на запиті без обовʼязкових полів. Клієнт, що надіслав такий запит, отримує збій сервера без пояснення замість помилки валідації і не може зрозуміти, що виправити в запиті.

**Докази**
- [BUG-003-missing-fields-500.txt](docs/bugs/BUG-003-missing-fields-500.txt): сирий запит і відповідь (`curl -i`) з кроку 1 і результат перевірки з кроку 2

**Автотест:** API-N2 у [tests/api/booking-negative.spec.ts](tests/api/booking-negative.spec.ts), позначений `test.fail()`. Спершу перевіряє, що бронювання не створено (проходить), потім що статус 4xx (падає: отримано 500). **Обмеження:** `test.fail()` зараховує як очікуване будь-яке падіння тесту. Якщо API почне ще й створювати неповне бронювання (гірша регресія), тест так само покаже «expected fail». Тому в звіті треба дивитися, на якому кроці він упав: очікуваний крок — «response is a 4xx client error».

## Спостереження

### OBS-01: сортування каталогу скидається після повернення з картки товару
**Оточення:** як у BUG-002.
**Кроки:**

3. Відкрити товар **Sauce Labs Onesie** (клік по зображенню).

**Що відбувається:** список повертається до порядку «Name (A to Z)», у dropdown обрано «Name (A to Z)».
**Чому не баг:** вимоги зберігати сортування між сторінками немає. Те, що вибір має зберігатися, — UX-припущення, яке потребує підтвердження від продукту.
**Докази:** [OBS-01-1-sorted-by-price.png](docs/bugs/OBS-01-1-sorted-by-price.png) (крок 2), [OBS-01-2-sort-reset-after-back.png](docs/bugs/OBS-01-2-sort-reset-after-back.png) (крок 4).

### OBS-02: запити телеметрії на backtrace.io отримують 401
**Оточення:** як у BUG-002.
**Що відбувається:** під час роботи з сайтом браузер надсилає `POST https://events.backtrace.io/api/unique-events/submit?universe=UNIVERSE&token=TOKEN` і `.../summed-events/submit?...` та отримує **401 Unauthorized**. У консолі це помилки «Failed to load resource». Параметри `universe` і `token` мають буквальні значення `UNIVERSE` і `TOKEN`.
**Чому не баг:** на функціональність для користувача не впливає. Чи телеметрія взагалі має працювати на демо-стенді, невідомо.
**Докази:** [OBS-02-console-errors.log](docs/bugs/OBS-02-console-errors.log): 4 помилки консолі за одну сесію (логін → кошик → чекаут).

Оточення для OBS-03…OBS-06 те саме, що в BUG-003 (curl 8.22.0, Windows 11 Pro 10.0.26200, UTC+02:00, 25.11.2026).

### OBS-03: API: `POST /auth` з невірним паролем повертає 200 OK
**Що відбувається:** на `{"username":"admin","password":"wrong-password"}` приходить `HTTP/1.1 200 OK` з тілом `{"reason":"Bad credentials"}`. Токен не видається.
**Чому не баг:** функціонально відмова працює: доступу немає, причину повідомлено (це перевіряє API-N3). Документація не обіцяє 401 і взагалі не описує помилок, тож контракт не порушено. Для клієнта це незручно, бо успіх і відмову доводиться розрізняти за тілом, а не за статусом, але це питання дизайну API, а не дефект.
**Докази:** [OBS-03-auth-bad-credentials-200.txt](docs/bugs/OBS-03-auth-bad-credentials-200.txt).

### OBS-04: API: `DELETE /booking/:id` повертає 201 Created
**Що відбувається:** успішне видалення повертає `HTTP/1.1 201 Created` з тілом `Created`.
**Чому не баг:** саме так показано в прикладі документації («HTTP/1.1 201 Created»), тож API робить задокументоване. За RFC 9110 201 означає «ресурс створено», а для видалення звичніші 200 або 204, тому це варто обговорити з автором API. API-01 очікує 201, як у документації.
**Докази:** [OBS-04-05-delete-201-and-repeat-405.txt](docs/bugs/OBS-04-05-delete-201-and-repeat-405.txt), запит 1.

### OBS-05: API: повторний `DELETE` уже видаленого бронювання повертає 405 Method Not Allowed
**Що відбувається:** після успішного видалення `GET` того ж id дає `404 Not Found`, а повторний `DELETE` дає `405 Method Not Allowed`.
**Чому не баг:** документація цей випадок не описує, а функціонально все гаразд: бронювання вже немає. За RFC 9110 405 означає, що метод не підтримується ресурсом, тож для відсутнього ресурсу логічніше 404, як і повертає `GET`. Автотесту немає.
**Докази:** [OBS-04-05-delete-201-and-repeat-405.txt](docs/bugs/OBS-04-05-delete-201-and-repeat-405.txt), запити 2 і 3.

### OBS-06: документація API неповна і місцями суперечлива
**Що помічено в [api_data.json](https://restful-booker.herokuapp.com/apidoc/api_data.json):**
- для жодного ендпоінта не описано відповідей з помилками (400, 401, 403, 404, 500 відсутні), хоча API їх повертає (403, 404, 405, 500);
- для DeleteBooking і HealthCheck мітка поля каже «Success 200», а приклад — «HTTP/1.1 201 Created».

**Наслідок для тестів:** очікування для негативних кейсів не можна взяти з документації; у тестах і README для кожного прямо вказано, звідки взято очікування.

## CI

Workflow: [.github/workflows/tests.yml](.github/workflows/tests.yml) (GitHub Actions).

**Коли запускається:** на кожен `push` у будь-яку гілку, на `pull_request` і вручну (кнопка **Run workflow**, `workflow_dispatch`). Новий push у ту саму гілку скасовує застарілий запуск того ж типу (`concurrency`). Push у гілку з відкритим PR запускає workflow двічі (`push` і `pull_request` мають різні `github.ref`); це свідомо не прибрано, бо ТЗ вимагає запуск саме на push, а дублювання коштує лише хвилин CI.

**Що робить:** два паралельні jobs, `ui tests` і `api tests` (matrix). У кожному: `npm ci` → `npm run typecheck` → для UI `npx playwright install --with-deps chromium` → `npx playwright test --project=<ui|api>`.

**Звіт як артефакт.** Після кожного запуску, навіть якщо тести впали, завантажуються:
| Артефакт | Що всередині |
|---|---|
| `playwright-report-ui`, `playwright-report-api` | HTML-звіт Playwright (`index.html`) |
| `test-results-ui`, `test-results-api` | `junit.xml` і папки тестів, що впали. Для неочікуваного падіння: UI — `trace.zip`, скриншот `test-failed-1.png`, `error-context.md`; API — `trace.zip`, `error-context.md`. Для тестів на відомі баги (expected fail) — лише `error-context.md`: Playwright з `trace: 'retain-on-failure'` не зберігає trace для очікуваного падіння |

Артефакти зберігаються 14 днів.

**Як відкрити звіт:**
1. Відкрити запуск у вкладці [Actions](https://github.com/Yarik0378/qa-automation-test-task/actions/workflows/tests.yml).
2. Унизу сторінки, у блоці **Artifacts**, завантажити `playwright-report-ui` або `playwright-report-api` і розпакувати.
3. Відкрити звіт: `npx playwright show-report <розпакована-папка>` (подвійний клік по `index.html` може не показати trace через обмеження браузера для локальних файлів).

**Відмінності від локального запуску** (з [playwright.config.ts](playwright.config.ts), за `CI=true`): `retries: 2`, `failOnFlakyTests`, `forbidOnly` (забутий `test.only` валить запуск), додатково репортер JUnit. **Flaky валить CI** (`failOnFlakyTests: true` у CI). Retries лишаються лише як діагностика: тест, що впав і пройшов з повторної спроби, позначається як **flaky**, і job стає червоним. Свідомий компроміс: публічний restful-booker на herokuapp інколи відповідає повільно, тож CI зрідка може червоніти не через наш код, зате нестабільність не ховається під зеленим бейджем. Перевірено локально з `CI=true` на тимчасовому тесті, що падає з першої спроби: `1 flaky`, код виходу 1.
